# Drillbench · 本地容灾演练台

一个完全跑在本地的容灾演练沙盒：把「按服务依赖恢复」扩展成 **依赖 × 配置漂移 × 证书有效期 × 恢复点新旧** 的联合排序，注入步骤超时后立即显示哪些服务能恢复、哪些必须等待，并在 RTO / RPO 无法同时达标时把两条候选路径的代价摆到操作者面前，由操作者确认后才落账。

## 运行

```bash
npm install
npm run dev      # http://127.0.0.1:4173
npm run build    # tsc -b + vite build，产物在 dist/
npm run preview  # 预览构建产物
npm test         # vitest run，22 个领域测试
```

所有状态写在 `localStorage` 的 `drillbench.workspace.v1`，不连任何后端；「重置」会清空台账、执行记录与操作者确认。

## 四个需求是怎么落地的

### 1. 排序不只按依赖

`src/domain/simulate.ts` 的调度器按分钟推进，每个步骤有一个可解释的排序权重（检查器里逐项显示）：

| 因子 | 作用 |
| --- | --- |
| 服务层级 | 核心服务先行 |
| 下游依赖数 | 解锁服务多的步骤先排 |
| 配置漂移 | 恢复前必须对齐的配置排在恢复之前 |
| 证书紧迫度 | 已过期或临近到期的证书抢占 PKI 通道 |
| 恢复点新旧 | 本地快照比备份库新，则恢复点更近的步骤先排 |

通道（config / pki / scan / restore / verify）各自有并行容量，恢复步骤要等自己的上游服务 `verify` 通过后才进入就绪队列。

### 2. 已执行的步骤不重复产生副作用

`src/domain/execution.ts` 里的幂等契约：

- 请求签名 = 场景版本 + 路径 + 目标 + 实际生效的超时。
- **同签名重复请求** → 回放：只把 `replays` 加一，不新开批次、不写台账、不重放任何副作用。
- **不同签名** → 台账仍然是权威：已记录的配置 / 证书副作用全部标记为「沿用」（`carried`，起始时间 -1，状态已完成），本次演练不再执行；对这些步骤注入超时也不会产生任何效果。

「副作用台账」页可以逐项核对每条副作用只落账一次，以及它属于哪个批次 / 请求。

### 3. 让某一步超时，再看谁能恢复

在时间轴上点选任意步骤，在检查器里填入小于计划耗时的超时值（或用 1′/2′/6′/12′ 预设）。

- 超时步骤标记为 `timed-out`，**不算干净完成**，它的下游全部被阻塞，进入「必须等待（上游未就绪）」。
- 自身没有上游问题、只是被自己链路中断的服务归入「不可用（自身链路失败）」。
- 其余分支照常恢复；可用服务数曲线与结论区会同步更新。
- 只要有一个核心服务不可用，RTO 就报告为「未全恢」而不是部分最大值。

### 4. RTO / RPO 不能同时满足时，先看代价

两条固定候选路径：

| | 先接管（延迟优先） | 先对齐（数据优先） |
| --- | --- | --- |
| 恢复点 | 本地快照（较新） | 备份库 + 归档日志 |
| 恢复通道 | 4 条 | 2 条 |
| 完整性校验 | 跳过 | 每服务 4–8′ |
| 配置范围 | 仅核心服务 | 全量 |
| 证书窗口 | 48 小时 | 30 天 |

默认目标 RTO 40′ / RPO 6′ 下：先接管 RTO 36′ / RPO 9′（守住时间、丢掉 3′ 数据），先对齐 RTO 64′ / RPO 2′（守住数据、超时 24′）。页面结论区写明「两条路径各有一项必须放弃」，点「查看代价对比」会打开确认对话框，列出每条路径的代价与收益；**确认前不写台账、不产生任何副作用**，勾选「我已知悉……」后按钮才可用。确认记录进入「操作者确认」页。

## 测试覆盖

`npx vitest run` 覆盖：场景与 DAG 自检、通道互斥、依赖顺序、证书抢占、两条路径的证书续期差异、超时传播（等待 / 失败 / RTO 为空 / 沿用步骤超时无效）、同签名回放与跨路径沿用、决定记录、代价清单与 RPO 受影响服务。
